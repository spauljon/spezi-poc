# hapi/ — HAPI FHIR deployment

Follow the root [CLAUDE.md](../CLAUDE.md) (data rules, milestone workflow, FHIR rules). The data rules apply here without exception: synthetic data only in fixtures, tests and logs.

- Stack: HAPI FHIR 7.6.0 (R4) in Docker (compose project `spezi-poc`): Oracle datasource (M1), TLS (M2), token verification and authorization (M4). No data in this directory.
- HAPI's 8443 is network-reachable since M4 because every `/fhir` request needs a verified token and nothing outside `/fhir` is served. Never publish a plain-HTTP or unauthenticated service on all interfaces.
- The extension (`ext/`) is a thin jar: every dependency is `provided` by the HAPI war (check `WEB-INF/lib` of `main.war` before adding one). Token verification and rules live in one interceptor, `PocAuthorizationInterceptor`, hooked at `POST_PROCESSED` with `order = -1` so it runs before the request validator (stock `PRE_HANDLED` runs after it, so an anonymous caller would get 422 and validator output instead of 401; reproduced, see README). Keep that order. There is deliberately no servlet filter. `UnusedEndpointRemover` deletes the stock image's `/control/jobs` and tester controllers; do not re-enable them without protecting them.
- Changing only `application.yaml` was observed NOT to be picked up by `make stack-up` (the container was left as it was; a mutation test passed vacuously because of it). Run `scripts/compose.sh up -d --force-recreate --no-deps hapi`, then confirm the change inside the container.
- Do not run write-capable checks against a build with authorization weakened. Only the capture role can delete, and only a Health Connect Observation by its sample identity inside a transaction (M27); stray data of any other kind needs an Oracle volume reset.
- Retraction (M21): the capture role's only update is the conditional status patch, guarded by `RetractionPolicy` and carried by `RetractionRule` (see README). Never widen either to make a request pass: HAPI's own patch rule does not match a conditional PATCH in 7.6.0, which is why the rule is ours. A change to the permitted request means changing both, `RetractionPolicyTest`, and the live cases in `hapi/auth.py`, with a refusal proved against the accepted request.
- Health Connect (M25): `healthconnect-sample` is a retraction system, the `healthconnect-group` system is deliberately NOT (it names every Observation a record produced: a lookup key, never a retraction key). `RetractionPolicyTest` and `retraction_checks_healthconnect` in `hapi/auth.py` pin both, with the accepted sample request as the control; `contract/check.py` keeps the configured list equal to the contract's.
- Update and delete (M27, decision A11): the capture role may, inside a transaction only, PUT or DELETE `Observation?identifier=<healthconnect-sample>|<value>` (conditional, one plain value, an update must carry that identifier and no id of its own beyond the entry's `urn:uuid` fullUrl). `ChangePolicy` (pure, unit-tested) judges the Bundle and `ChangeRule` is added to that request's rules only after it accepted every PUT and DELETE; a direct PUT or DELETE, an id in the URL, the group system, the HealthKit or synthetic systems, any second parameter and another resource type are refused (`ChangePolicyTest`, and `change_checks_healthconnect` in `hapi/auth.py`, each refusal beside the accepted request). `poc.auth.change-identifier-systems` in `application.yaml` is checked equal to the contract's Health Connect sample system. HAPI's delete is soft (a new version, `_history`, 410 on read); a conditional PUT that matches nothing creates a NEW resource, it does not resurrect the deleted one. Observed: HAPI passes the existing resource as the rule's "output" when it checks an update or delete, so `ChangeRule` matches the operation, not the absence of an output.
- HAPI's counts above 9,999 are not reliable (observed 2026-11-17: the `total` of an unfiltered `Observation/_history` did not move through 5 deletes), and a paged `_history?_since=` has no `total` at all. Check a delete or an update by reading the entries (method per entry, as `scripts/android-hc-counts.py --history <time>` does) or by searching one identifier, never by a large count.
- Tests: `make test-hapi` (extension unit tests, run in the image build); `python3 hapi/auth.py check` (live matrix, needs the stack); `make test` runs the first and `make stack-verify` runs the second.
- Never touch the governance project's HAPI or its files; copy and adapt only (provenance is in README.md).
- Milestones: M1, M2, M4, M21, M25, M27
- Contract: codes, units and categories come from `contract/metrics.json` (added in M6), never hand-copied.
- Commit prefix: `hapi:`
